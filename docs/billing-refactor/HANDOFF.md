# دليل التسليم — إعادة هيكلة قسم الدفع/الفوترة

هذا الملف مرافق لـ `billing_refactor_prompt.md`. لا تحتاجه للتنفيذ، لكنه يوضح **كيف يُسلَّم وكيف يُتابَع**.

---

## 1) ما هو الملف؟

`billing_refactor_prompt.md` هو **البرومبت التنفيذي الكامل** (ملف واحد مكتفٍ بذاته) لإعادة هيكلة قسم الدفع إلى نموذج **«الفاتورة أولاً»**: الموقع يبني الفاتورة وبنودها، وبوابة الدفع تحصّل المبلغ فقط.

يحتوي على:
- الدور والسياق (القسم 0)
- نتائج الفحص المكتمل كخط أساس (القسم 1) — **لا تُعَد**
- المسار المستهدف بالتفصيل + جدول تصنيف المسارات (القسم 2)
- القيود الصارمة (القسم 3)
- المراحل 1–10 بنطاقها ومعايير قبولها واختباراتها (القسم 4)
- بوابات القبول لكل PR + حالات التوقّف الفوري (القسم 5)
- معايير الإنجاز النهائية (القسم 6)
- بروتوكول العمل ونقاط الرجوع (القسم 7)

---

## 2) أين يوضع في المستودع؟

أي من هذه الخيارات مقبول، وكلها تعني الشيء نفسه: الملف داخل المستودع ومقروء من الأدوات:

| الموضع | مناسب لـ |
|---|---|
| `docs/billing_refactor_prompt.md` | الأكثر شيوعًا، ويُشار إليه من README |
| `.agents/billing_refactor_prompt.md` | إن كان المستودع يستخدم مجلد `.agents/` |
| `.cursor/rules/` أو `CLAUDE.md` | إن أردت أن يقرأه الوكيل تلقائيًا في كل جلسة |
| `AGENTS.md` (رابط للملف) | لتوحيد نقطة الدخول لكل الأدوات |

**مهم:** لا تنسخ محتوى الملف داخل `AGENTS.md` أو `CLAUDE.md` — ضع رابطًا أو أشِر إلى المسار، حتى يبقى هناك مصدر واحد للتحديث.

## 3) ترتيب المراحل

```
1. جدول بنود الفاتورة + backfill + تصنيف الـ14 فاشلًا   ← ابدأ هنا حصرًا

3. Quote endpoint

5. تحويل مسارات التجاوز إلى invoice-first          ← توقّف واعتمد القرار
6. تحصين الـ webhook
7. الشحن ولغة الكتاب كبنود فاتورة
8. إغلاق الاختبارات الـ14
9. إصلاح coaching_plus + حذف .bak + حاجز CI
10. تفكيك CheckoutForm.tsx (اختيارية، أخيرًا)
```

كل مرحلة = **PR واحد**. لا تُقبل دفعة واحدة تشمل عدة مراحل.

## 4) معايير القبول — الصورة المختصرة

بوابة القبول في كل PR:

```
□ npx tsc --noEmit            → صفر أخطاء
□ next build                  → نجاح
□ اختبارات الدفع              → الفاشلون ≤ 14 حتى المرحلة 8، ثم 0
□ لا *.bak ولا نسخ احتياطية
□ لا تغيير في إعداد/مفاتيح أي بوابة
□ migrations إضافية فقط + خطة رجوع
□ لا اختبار معطّل أو توقع معدّل ليمرّر البناء
□ لا 404/500 جديدة على المسارات القائمة
```

ومعيار الإنجاز النهائي للقسم كله: **كل مسار دفع مصنّف `invoice-first`**، وصفر مسار يتجاوز الفاتورة بلا قرار بشري موثّق.

## 5) «لا تُعِد Phase 0»

الفحص **مكتمل ولا يُعاد**. هذه نتائجه، وهي نقطة انطلاق المطوّر:

| البند | النتيجة |
|---|---|
| `tsc --noEmit` | نظيف |
| `next build` | ناجح |
| اختبارات الدفع | **14 فاشلًا في 5 ملفات** |
| جدول بنود الفاتورة | **غير موجود** |
| مصادر الأسعار | **9+ مواضع متعارضة** |
| مسارات تتجاوز الفاتورة | **3 مؤكدة**: Kashier quick links، Kashier service links، Paymob direct/standalone |

إن طلب المطوّر إعادة الفحص، فأجب: «الخط الأساس موثّق في القسم 1 — ابدأ من المرحلة 1». إعادة الفحص تكلّف دورة كاملة بلا فائدة.

## 7) كيف تُراجع التسليم؟

لا تقبل «تم» بلا أرقام. اطلب في كل PR:

- ما تغيّر (ملفات ومسارات).
- ما لم يتغيّر (إثبات عدم المسّ بالإعدادات والمسارات).
- الاختبارات المضافة + نتيجتها.
- مخرَجات `tsc` / `next build` / حزمة الدفع **مقارنة بالخط الأساس (14 فاشلًا)**.
- خطة الرجوع.

وإن قال «أصلحت» — اطلب الأمر الذي شغّله والنتيجة التي رآها.
