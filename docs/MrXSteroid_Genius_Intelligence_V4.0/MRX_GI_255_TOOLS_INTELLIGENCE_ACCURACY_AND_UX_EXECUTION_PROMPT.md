# 4. RESULT QUALITY — REPLACE GENERIC OUTPUT WITH DOMAIN-SPECIFIC REPORTS

The current user-facing text is not acceptable when it merely says:

- calculation complete;
- number of required inputs supplied;
- result type CALCULATED;
- long repeated disclaimers;
- generic statements unrelated to the actual result.

These are operational metadata, not a complete user report. Move technical state and input-count details to a compact status/diagnostic area (or expandable details) unless they are directly useful to the user.

## 4.1 Result Narrative Contract

For each tool, design a concise but substantive result narrative using only validated values and relevant context. Depending on the domain, include:

1. **Primary result:** clear result, units and classification.
2. **Personalized interpretation:** what this value means for this tool and the specific entered data.
3. **Why:** calculation/method, relevant inputs and the factors that materially affected the result.
4. **Current status:** the user's current measured/calculated state compared with a relevant validated range or their declared goal.
5. **General guidance:** useful, actionable guidance specific to the tool.
6. **Specialized guidance:** health, training, nutrition, finance, or other domain-specific guidance only where relevant and supported.
7. **Recommendations:** prioritized next steps with a reason and expected purpose.
8. **Scenarios / What-If:** show how changes to meaningful inputs alter the result.
9. **Forecast:** only if a validated predictive or statistical method and suitable time-series/context data exist. Include horizon, assumptions and uncertainty. A static calculator must not invent a future outcome.
10. **Limitations and safety:** concise, relevant limits; place detailed disclaimers in an expandable section rather than repeating them in every card.
11. **Evidence and provenance:** source/method/version and freshness when relevant.
12. **Next step:** the most relevant next action or connected tool, without automatic external actions.

Do not generate a section merely to fill a template. Return `NOT_APPLICABLE` or omit the section with a clear reason when unsupported.

## 4.2 Five result panels — meaningful, dynamic and conditional

Design these reusable panels, adapting names and content to each tool:

- **Smart Advice:** a specific practical recommendation based on the current result and declared goal.
- **Prediction / What Happens Next:** only a supported forecast or scenario; never an invented prediction.
- **Medical / Specialist Guidance:** shown only for relevant health, fitness, nutrition, hormone, lab or medication tools; informational, evidence-based, non-diagnostic and with appropriate escalation.
- **Current Status:** the current state, range, trend or goal comparison that can genuinely be derived.
- **Current Feeling / User Check-in:** must primarily use a feeling/symptom/status explicitly reported by the user. Do not infer emotions, pain or symptoms from BMI, weight, water intake or other weak proxies.

Each panel must be driven by a typed result/context contract and update when a relevant input changes. Clearly show when data is insufficient. Do not make the five panels identical across tools.

## 4.3 Avoid boilerplate and repetitive disclaimers

- Do not repeat the same disclaimer in the headline, result card, narrative and every panel.
- Keep safety caveats visible but proportionate and contextual.
- Do not show internal implementation labels such as `SUFFICIENT_FOR_BASIC_RESULT` as the main user explanation.
- Technical statuses (`CALCULATED`, `RULE_BASED`, etc.) may appear in a compact provenance/details area; translate them naturally for users.
- Explain the actual result, not merely the process that produced it.
- Use clear Arabic and English copy. Avoid literal translation that produces awkward or contradictory phrasing.
- Every statement must be traceable to an input, validated rule, formula, source or explicitly labeled estimate.

## 4.4 BMI-specific interpretation example

BMI's core formula is a defined screening calculation; do not invent a replacement formula or pretend BMI directly measures body fat. Improve the tool by presenting the calculated BMI, validated category applicability, a meaningful explanation of what BMI can and cannot tell the user, and relevant contextual limitations (for example, age group and individual body composition where applicable). Ask for additional context only if the product design and evidence support its use. Do not infer a person's feelings, diagnosis or treatment from BMI alone.

Apply the same principle to every other tool: improve contextual interpretation and supported inputs without corrupting a valid underlying formula.

# 5. FORMULA INTELLIGENCE — DOMAIN-SPECIFIC CALCULATION IMPROVEMENT

Audit formulas and calculation methodology for every tool. The aim is higher domain accuracy, not the arbitrary addition of complexity.

For each tool:

1. Identify the exact formula/algorithm currently executed in code.
2. Record authoritative domain references, source dates/versions and intended population/use case.
3. Identify assumptions, supported input ranges, excluded populations and known limitations.
4. Compare the implementation with the reference calculation using independent golden cases.
5. Identify whether the method is deterministic, rule-based, statistical estimate or actual model prediction.
6. Check units, normalization, precision, rounding, boundaries, missing data and invalid values.
7. Evaluate whether multiple validated methods are needed for different user contexts; if so, expose method choice or select transparently using validated rules.
8. Add uncertainty/limitations and source provenance.
9. Add regression tests before and after any change.
10. Do not change a scientifically established formula merely to make the output look more intelligent.

For health-related tools, use current, reputable clinical/public-health sources and expert review where appropriate. Do not invent a personalized medical recommendation or claim a validated prediction without supporting evidence. If methods conflict, document the alternatives and ask for owner approval before a material behavior change.

## 5.1 Calculation authority

Deterministic engines remain authoritative for numerical outputs. AI may explain, summarize or suggest; it must never silently overwrite engine results or formula constants. Every displayed number must map to an engine result, validated rule or explicitly labeled estimate.

# 6. DYNAMIC INPUTS, SLIDERS AND PRECISE ENTRY

For every tool, assess which numeric fields benefit from a slider. Use sliders only where they suit the data type and valid range.

A suitable slider field must provide:

- Animated/interactive track and thumb, with smooth but restrained motion.
- Domain-appropriate tick marks and labels.
- Correct minimum, maximum and step.
- Current displayed value and unit.
- Synchronized precise numeric input.
- Immediate validation and clear error feedback.
- Keyboard, touch, mouse and screen-reader support.
- Reduced-motion support.

Manual numeric entry must remain available; the slider is not a replacement for precise input. Slider and number input must share one canonical state and remain synchronized in both directions.

## 6.1 Measurement-aware scale

The slider must be connected to the existing global measurement control in the Header. Do not build a separate per-tool preference system.

When the user switches among supported systems (Metric, Imperial and US Customary where applicable):

- Update the unit label.
- Update the actual displayed minimum and maximum.
- Update step and tick marks according to the field's precision and domain range.
- Update the displayed value and precise input.
- Preserve the same canonical physical quantity.
- Recalculate only from the canonical value; never reconvert an already converted display value.
- Update dependent calculations and visualizations without a page reload.

Do not merely rename `kg` to `lb` while leaving the same numeric scale. Metric, Imperial and US Customary are not interchangeable labels; define supported units per field.

Create field-level metadata for canonical unit, accepted/display units, canonical/display min/max, step, precision, conversion functions and validation constraints. Do not invent arbitrary bounds simply to make a slider render. If the possible range is too broad or continuous for a slider, use an appropriate alternative control.

## 6.2 Global measurement integration

Test the Header measurement control with every relevant shared component and tool. Validate changes before input, after input, after results, during What-If, through repeated switching and when navigating between tools. Preserve saved preference only through the existing approved preference mechanism.

- Interactive tooltips that work with hover, focus and touch.

# 12. REQUIRED TEST MATRIX

## 12.1 Calculation and domain correctness

- Golden/reference cases for normal, boundary, decimal and exceptional inputs.
- Missing, invalid, negative, zero, non-finite, impossible and out-of-range data.
- Formula version and source traceability.
- Unit normalization and repeated round-trip conversion.

## 12.2 Result quality

- No generic filler as the primary report.
- Every narrative statement is grounded in actual result, input, rule, model or source.
- Relevant panels contain tool-specific information.
- Unsupported forecast/medical/feeling panel is omitted or explicitly marked not applicable.

## 12.3 Header and dynamic input

- Language switch updates the complete page without stale text.
- Measurement switch updates real units, values, ranges, steps and marks.
- Metric → Imperial → Metric round-trip preserves canonical value within defined tolerance.
- Slider movement updates precise input and calculation.
- Manual entry updates slider and calculation.
- Invalid text, paste, keyboard and touch input are handled correctly.
- No double conversion, stale state, infinite render/recalculation loop or page reload.

## 12.4 Browser, responsive and accessibility

- Real browser checks at desktop and mobile, including 375px viewport.
- Arabic RTL and English LTR.
- Keyboard-only slider and form operation.
- Screen-reader labels, values, errors and dynamic announcements.
- axe audit or equivalent with a recorded report.
- Focus states, contrast, touch targets and reduced motion.
- No horizontal overflow, clipped values, obscured controls or layout jumps.

## 12.5 Regression and platform integration

- Run relevant integration/contract/registry checks.
