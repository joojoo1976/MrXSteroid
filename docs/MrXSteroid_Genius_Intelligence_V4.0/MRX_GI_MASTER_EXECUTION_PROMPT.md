# 8. RESULT QUALITY — DOMAIN-SPECIFIC REPORTS, NOT GENERIC FILLER

## 8.1 Principle

A result is not acceptable when the primary user-facing report merely says:

- "calculation complete";
- "number of required inputs supplied";
- "result type CALCULATED";
- long repeated disclaimers;
- generic statements unrelated to the actual result.

These are operational metadata. Move technical state and input-count details to a compact status/diagnostic area or expandable details unless they are directly useful to the user.

## 8.2 Result narrative contract

For each tool, design a concise but substantive result narrative using only validated values and relevant context. Depending on the domain, include:

1. **Primary result:** clear result, units and classification.
2. **Personalized interpretation:** what this value means for this tool and the specific entered data.
3. **Why:** calculation/method, relevant inputs and the factors that materially affected the result.
4. **Current status:** the user's current measured/calculated state compared with a relevant validated range or declared goal.
5. **General guidance:** useful, actionable guidance specific to the tool.
6. **Specialized guidance:** health, training, nutrition, finance or other domain-specific guidance only where relevant and supported.
7. **Recommendations:** prioritized next steps with a reason and expected purpose.
8. **Scenarios / What-If:** how changes to meaningful inputs alter the result.
9. **Forecast:** only if a validated predictive or statistical method and suitable time-series/context data exist. Include horizon, assumptions and uncertainty. A static calculator must not invent a future outcome.
10. **Limitations and safety:** concise, relevant limits; detailed disclaimers belong in an expandable section rather than repeated in every card.
11. **Evidence and provenance:** source, method, version and freshness when relevant.
12. **Next step:** the most relevant next action or connected tool, without automatic external actions.

Do not generate a section merely to fill a template. Return `NOT APPLICABLE` or omit the section with a clear reason when unsupported.

## 8.3 Comprehensive report components

Depending on domain suitability, a tool's report may include:

1. Primary Result.
2. Executive Summary.
3. Current Status.
4. Professional Interpretation.
5. Why This Result?
6. Calculation Method.
7. Important Factors.
8. Strengths and Limitations of the Result.
9. Personalized Recommendations.
10. General Advice.
11. Safety / Medical Guidance when applicable.
12. Future Outlook / Predictions when supported.
13. What-If Scenarios.
14. Sensitivity Analysis.
15. Charts and Visual Explanations.
16. Uncertainty and Data Quality.
17. Practical Next Steps.
18. Related Tools.
19. Detailed Report.
20. Export / Save / Share when implemented and authorized.

This is a **menu**, not a mandatory checklist. Every included component must be supported by the tool's domain, inputs and evidence. Unsupported components are omitted or labeled `NOT APPLICABLE` with a reason.

## 8.4 Dynamic explanation

The explanation must be tied to the actual inputs. Do not reuse the same paragraph for every user. Explanations vary with:

- User values.
- The result.
- The domain.
- Input completeness.
- The declared goal.
- Material factors.
- Assumptions.
- Limitations.

When an input changes, the related explanation must change.

## 8.5 Five smart result panels

Use the following reusable panels, adapting names and content to each tool:

### 1. Smart Advice
A specific practical recommendation based on the current result and declared goal, with the reason for the advice, its priority and the next step.

### 2. Predictions / What Happens Next
Only a supported forecast or scenario, with duration/horizon, influencing factors and uncertainty. Never an invented prediction.

### 3. Medical / Specialist Guidance
Shown only for relevant health, fitness, nutrition, hormone, lab or medication tools. Informational, evidence-based, non-diagnostic, with appropriate escalation.

### 4. Current Status
The current state, classification, indicators, range, trend or goal comparison that can genuinely be derived.

### 5. Current Feeling / User-Reported State
Primarily the feeling, symptom or status explicitly reported by the user. A limited, explicitly labeled estimate may be used only when data and method support it. Do not infer emotions, pain, symptoms or medical states as facts from BMI, weight, water intake or other weak proxies.

Each panel must be driven by a typed result/context contract and update when a relevant input changes. Clearly show when data is insufficient. Do not make the five panels identical across tools. Do not show a panel that is irrelevant to the domain or unsupported by its data.

## 8.6 Tool-specific comprehensive reports

Each tool needs a report specialized in its function. Do not use one textual template for all tools. Examples:

- **BMI:** analysis of the indicator, its limits, its interpretation, what it does not measure and appropriate scenarios.
- **Protein Needs:** analysis of protein requirement, goal, coefficients, recommendations and calculation limits.
- **Water Intake:** analysis of the fluid estimate, the factors that affected it, units and assumptions.

Every report must explain the result, not merely repeat it.

## 8.7 Anti-boilerplate and disclaimer proportionality

- Do not repeat the same disclaimer in the headline, result card, narrative and every panel.
- Keep safety caveats visible but proportionate and contextual.
- Do not show internal implementation labels such as `SUFFICIENT_FOR_BASIC_RESULT` as the main user explanation.
- Technical statuses (`CALCULATED`, `RULE_BASED`, etc.) may appear in a compact provenance/details area; translate them naturally for users.
- Explain the actual result, not merely the process that produced it.
- Use clear Arabic and English copy. Avoid literal translation that produces awkward or contradictory phrasing.
- Every statement must be traceable to an input, validated rule, formula, source or explicitly labeled estimate.

## 8.8 BMI interpretation example

BMI's core formula is a defined screening calculation. Do not invent a replacement formula or pretend BMI directly measures body fat. Improve the tool by presenting:

- the calculated BMI;
- validated category applicability;
- a meaningful explanation of what BMI can and cannot tell the user;
- relevant contextual limitations (for example age group and individual body composition where applicable).

Apply the same principle to every tool: improve contextual interpretation and supported inputs without corrupting a valid underlying formula.

# 10. ADVANCED DYNAMIC INPUTS, SLIDERS AND PRECISE ENTRY

## 10.1 Suitability rule

For every tool, assess which numeric fields benefit from a slider. Use sliders only where they suit the data type and valid range. If a range is too broad, continuous or irregular, use a better control while preserving data precision.

## 10.2 Slider requirements

A suitable slider field must provide:

- A graduated input track.
- An animated but restrained smooth thumb.
- Clear tick marks and labels.
- Correct minimum, maximum and step.
- Prominent current value.
- Current unit.
- Dynamic fill movement.
- Value updates while dragging.
- Mouse and touch interaction.
- Keyboard support.
- Screen-reader support.
- Update without page reload.
- Immediate validation and clear error feedback.
- Reduced-motion support.

## 10.3 Precise manual input

Manual numeric entry must remain available; the slider is not a replacement for precise input. Place a precise numeric field beside the slider.

When the slider moves:

- The precise field value changes.
- The calculation changes.
- The result changes.
- Related warnings change.
- Related charts change.

When a number is entered manually:

- The slider moves to the correct position.
- The value updates.
- The field range is validated.
- The results update.

Both controls must share one state source, with no divergence, conflict or rebound.

## 10.4 Dynamic field configuration

Every numeric field must define, according to its domain:

- Canonical min / max / step.
- Display min / max / step.
- Precision.
- Marks.
- Accepted units.
- Canonical unit.
- Validation rules.
- Unit conversion functions.
- Accessibility metadata.

Do not use the same scale for all field types.

## 10.5 Measurement-aware scale and conversion order

Connect every slider and numeric field to the existing global measurement control in the Header. Do not build a separate per-tool preference system.

Conversion order:

`Canonical Value → Display Conversion → Slider Mapping`

When the user switches among supported systems:

- Update the unit label.
- Update the actual displayed minimum and maximum.
- Update step and tick marks according to the field's precision and domain range.
- Update the displayed value and precise input.
- Update tooltips.
- Update units inside results, charts and reports.
- Preserve the same canonical physical quantity.
- Recalculate only from the canonical value; never reconvert an already converted display value.
- Update dependent calculations and visualizations without a page reload.

Supported systems:

- **Metric** and **Imperial** are the currently supported systems in the product.
- **US Customary** is conditional: it may be added only where the existing preference system supports it and the owner approves it. Do not invent support.
- Do not merely rename `kg` to `lb` while leaving the same numeric scale.
- Define supported units per field.

Test repeated switching:

`Metric → Imperial → Metric → Imperial`

Prove:

- No accumulated conversion error.
- No double conversion.
- The canonical value is unchanged.
- The engine receives only the canonical unit.

## 10.6 Global measurement integration tests

Test the Header measurement control:

- Before input.
- After input.
- After results.
- During What-If.
