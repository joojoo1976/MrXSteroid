## 3. Approved Development Boundaries

Upon activation (2026-11-09), development proceeds per the Gate sequence G-R6.1-1 → G-R6.1-6, bounded by:

1. **No database writes, migrations, or production RLS changes** without separate authorization. W18 applies: no guest/session/cloud synchronization/database implementation until the owner explicitly approves it.
2. **No Supabase writes or RLS modifications.**
3. **No paid AI/provider activation or external API spending** without separate authorization.
4. **No production deployment** without owner-authorized release.
5. **No push, merge, rebase, or deployment.** Local commits are authorized only where the owner has granted commit permission (this activation commit; subsequent commits require instruction).
6. **No deleting or replacing existing work** (V4 migration, frozen tools 111/132/137/138/139, pilots, Phase 1/2 components). Completed infrastructure (R6ToolShell, R6Progress, ResultBoxes, Phase 0–2 batches, P2-A→E) is preserved and not rebuilt.
7. **No activating R6.1 features** (RAG, AI Core, cross-tool graph, voice/vision, canary) ahead of their gate sequence. In particular: no RAG before tenant isolation; no AI rollout before foundational contracts and policies; no canary before observability and tested kill/rollback; no expansion before successful pilot acceptance.
8. **No claiming acceptance without evidence.** Tenant/RLS acceptance requires negative isolation tests and actual evidence. G-R6.1-1 is not PASS until all its mandatory requirements and evidence are satisfied.

### 3.1 V4/V6 Architecture Resolution (Owner Directive §5)

Adopt a compatible, additive architecture:

- **V4** provides reusable presentation, contracts, adapters and domain profiles where appropriate.
- **Existing V6 deterministic engines remain authoritative** for their established calculations. No blanket migration or engine replacement.
- **V4 integrates through explicit, validated adapters.** Each integration requires meaningful tests and evidence.
- Existing approved tool identities and routes remain intact.
- Dashboard authentication work remains a separately traceable workstream — not silently committed, reverted, or merged.
