## المبدأ الحاكم في R6 - منصة تعرف نفسها
هدفنا ليس اكبر عدد من مزايا AI. هدفنا منصة ذكية تعرف: ماذا تستطيع فعله، وماذا لا تستطيع فعله، ومن اين جاءت بياناتها، ولماذا اصدرت النتيجة، وما تكلفة ذلك، وكيف نوقفها ونستعيد النظام عند الفشل.
هذا هو الفرق بين موقع يحتوي على ادوات بها AI، وبين MrXSteroid Genius Intelligence Platform كنظام سحابي ذكي متكامل وقابل للتوسع والحوكمة.
كل اداة وكل ميزة AI في R6 يجب ان تعلن عقد قدرة صادق قبل ان تعمل. بلا هذا العقد: لا اطلاق، ولا ادعاء ذكاء.

### عقد القدرة الصادق - Capability Truthfulness Contract (الزامي لكل اداة وكل ميزة AI)
لكل اداة ولكل ميزة AI، يجب ان يعلن النظام صراحة في الواجهة وفي السجل:
1. **CAN - ماذا نستطيع:** ما تحسبه الاداة فعلا، بالصيغة والمدخلات والنطاق المختبر.
2. **CANNOT - ماذا لا نستطيع:** ما لا تحسبه، وما لا تشخصه، وما لا توصي به، وما يتطلب طبيبا او مختبرا او قياسا حقيقيا.
3. **SOURCES - من اين جاءت البيانات:** كل مصدر: الاسم + الناشر + تاريخ النشر + تاريخ المراجعة + مستوى الدليل + رابط او مرجع قابل للتحقق. بلا مصدر = بلا اجابة طبية.
4. **WHY - لماذا اصدرت النتيجة:** خطوات الاستدلال + الصيغة المستخدمة + المدخلات الفعلية + الافتراضات + عدم اليقين. النتيجة بلا سبب مرفوضة.
5. **COST - ما التكلفة:** تكلفة الطلب (Tokens + وقت + مال تقديري) + الميزانية المتبقية + ما يحدث عند السقف (Fallback حتمي).
6. **STOP - كيف نوقفها:** زر/مفتاح الايقاف + مالك الايقاف + زمن التفعيل + ما يظهر للمستخدم بعد الايقاف.
7. **RESTORE - كيف نستعيد النظام:** خطة الاستعادة + RPO/RTO + اخر Drill ناجح + ماذا يحدث لبيانات المستخدم اثناء الفشل.
اي ميزة لا تستطيع ملء هذه الخانات السبع تظل بحالة NOT_SHIPPABLE، مهما كان اسمها ذكيا.

## النقطة الفاصلة 1 - الفصل بين غياب الدليل وغياب التنفيذ
هذا هو الخطأ الاخطر في كل الملفات السابقة: تحويل (لم نجد دليلا) الى (غير موجود)، او تحويل (وجدنا ادعاء) الى (موجود ومختبر). R6 يفصل بينهما نهائيا.

### مفردات الحالة - Status Vocabulary (الوحيدة المسموح بها)
| الحالة | معناها الدقيق | هل تعني التنفيذ موجود؟ | هل تعني التنفيذ غائب؟ |
|---|---|---|---|
| VERIFIED_PRESENT | وجدنا ملفا + اختبارا ناجحا + تشغيلا حيا يثبت وجود الميزة | نعم، بالدليل | لا |
| VERIFIED_ABSENT | بحثنا في الاماكن الصحيحة ووجدنا دليلا ايجابيا على الغياب (مثال: Route يرد 404 + Registry لا يحتوي الاداة + لا ملف محرك) | لا | نعم، بالدليل |
| UNKNOWN_NO_EVIDENCE | لم نبحث بعد، او بحثنا ولم نجد ولم نثبت الغياب | لا نعرف | لا نعرف |
| CLAIM_UNVERIFIED | شخص او تقرير ادعى الوجود، لكن لم يقدم ملفا او اختبارا او تشغيلا | لا نعرف | لا نعرف |
| PARTIAL_EVIDENCE | جزء موجود (مثال: واجهة موجودة لكن المحرك غير مختبر) | جزئيا فقط | جزئيا فقط |
| BLOCKED | لا نستطيع البحث (لا صلاحية، لا وصول، اداة مقفلة) | لا نعرف | لا نعرف |
قاعدة ذهبية: UNKNOWN_NO_EVIDENCE و CLAIM_UNVERIFIED و BLOCKED لا تتحول ابدا الى VERIFIED_PRESENT او VERIFIED_ABSENT بالاستنتاج او بالتكرار او بالثقة. تتحول فقط بدليل جديد.

### سلم الادلة - Evidence Ladder (E0 الى E5)
| المستوى | الدليل | مثال | يكفي لقبول؟ |
|---|---|---|---|
| E0 | لا دليل | لا ملف، لا سجل | لا |
| E1 | ادعاء | تقرير يقول مكتمل | لا - يظل CLAIM_UNVERIFIED |
| E2 | ملف موجود | ملف محرك او صفحة موجود في المستودع | لا - يثبت الوجود فقط، لا الصحة |
| E3 | اختبار ناجح قابل لاعادة التشغيل | Vitest 46/46 يمر من Clone نظيف | نعم للمنطق، لا للتشغيل الحي |
| E4 | تشغيل حي | Build اخضر + تشغيل في Staging/Prod مع سجل | نعم للتشغيل |
| E5 | تدقيق مستقل | مراجعة ثانية + سجل تدقيق + Game Day او Drill | نعم للقبول النهائي |
مثال التطبيق: Tool 111 له E2 (ملف موجود) لكنه فشل في E4 (Build Error Unterminated regexp) - لذلك حالته PARTIAL_EVIDENCE، وليست مكتملا ولا غائبا. واداة تظهر في الصفحة العامة فقط لها E1 على الاكثر للتنفيذ الداخلي - لذلك حالتها CLAIM_UNVERIFIED او UNKNOWN_NO_EVIDENCE، وليست VERIFIED_PRESENT.

### كيف نطبق الفصل في كل ملف لاحق
1. كل جدول مطابقة يجب ان يحمل عمودين منفصلين: عمود الحالة (من المفردات الستة) وعمود الدليل (E0-E5 + رابط الملف/الاختبار/السجل).
2. ممنوع كتابة موجود او غير موجود بلا عمود دليل.
3. ممنوع تحويل BLOCKED (اداة مقفلة لا نستطيع فحصها) الى غائب. المقفلة تعني لا نعرف، وليست غير موجودة.
4. ممنوع تحويل CLAIM_UNVERIFIED (تقرير Batch A/B) الى VERIFIED_PRESENT. التقرير يصبح دليلا فقط عندما يطابق مع ملف + اختبار + تشغيل.
5. كل قرار اطلاق يجب ان يذكر: ما نعرفه، وما لا نعرفه، وما هو BLOCKED، وما هي المخاطرة المتبقية.

## 2. عشرون اقتراحا للتطوير السحابي - 20 اقتراحا (ديناميك + AI + عام للادوات)
كل اقتراح يتضمن: المشكلة التي يحلها، التصميم، العقد/المخرج، القبول. لا يلغي اي اقتراح سابق - كلها اضافات فوق R3/R4.

### مجموعة ا: الديناميك - Dynamic (1-7)

**1 - Dynamic Input Contract v2 - عقد ادخال ديناميكي موحد**
المشكلة: كل اداة تعرف مدخلاتها بطريقتها، فينتج حقول ناقصة واخطاء تحقق غير متسقة. التصميم: مخطط Typed واحد لكل اداة: fieldId + label AR/EN + type + unit + range + required + dependsOn + visibilityRule + helpText + example. الحالات: Empty (لا نتيجة، بل ارشاد ماذا ينقص) - Partial (نتيجة اولية مع تحذير نقص) - Full (نتيجة كاملة). القبول: اختبار لكل اداة يمر بـ Empty/Partial/Full + رسائل خطا واضحة بالعربية والانجليزية.

**2 - Dynamic Result Engine - محرك نتائج ديناميكي حتمي**
المشكلة: نتائج Static لا تتحدث مع تغير المدخلات. التصميم: كل تغيير مدخل يعيد حسابا حتميا فوريا (Debounced)، مع Minimum Viable Output (MVO) - اقل نتيجة مفيدة حتى مع مدخلات جزئية - + Uncertainty + Evidence + FormulaUsed + UnitUsed. لا يخمن المحرك قيما غير مدخلة. القبول: اختبار يثبت ان نفس المدخلات تعطي نفس المخرجات دائما، وان MVO يظهر مع Partial دون اخفاء النقص.

**3 - Dynamic Cross-Tool Graph - شبكة ادوات ديناميكية بعقود و Freshness**
المشكلة: روابط Cross-Tool موجودة لكن بلا عقود ملزمة او عمر بيانات. التصميم: كل رابط = عقد: sourceToolId + targetToolId + mappedFields + freshnessRule + staleAction (تحذير/حظر/طلب تحديث). جدول Freshness ملزم: مثال Body Fat 7 ايام، Sleep 1 يوم، Lab 90 يوما (قابل للمراجعة من المالك والمرجع الطبي العام - ليس وصفة). حدث Event Bus mrx_tool_result_updated يحمل toolId + timestamp + version + freshness. القبول: اختبار Stale يثبت ظهور تحذير عند انتهاء العمر، واختبار يثبت عدم تسرب بيانات مستاجر لاخر عبر الرابط.

**4 - Dynamic Units & Localization Engine - محرك وحدات ومناطق بلا Double Conversion**
المشكلة: خطر تحويل مزدوج يعطي ارقاما صحية خاطئة. التصميم: كل المحركات داخليا Metric فقط. التحويل يحدث مرة واحدة عند الادخال (الى Metric) ومرة واحدة عند العرض (من Metric)، مع دالة واحدة مركزية + اختبارات Golden. دعم AR/EN + RTL/LTR + Timezone + تنسيق الارقام والتواريخ + وحدات kg/lb و cm/in و kcal/kJ. القبول: اختبار Double Conversion سلبي لكل محرك + اختبار RTL + اختبار Timezone.

**5 - Dynamic Preferences & Session - تفضيلات وجلسات ديناميكية للزائر والمسجل**
المشكلة: مصير حفظ حالة الزائر غير محسوم. التصميم: قرار موثق: الزائر = حفظ محلي فقط (Local) مع تحذير انه قد يضيع، بلا ارسال للسحابة. المسجل = حفظ سحابي مشفر مع مزامنة + حل تعارض (Last-Write-Wins مع سجل + خيار للمستخدم). PreferencesProvider واحد: units + language + theme + voice + AI settings + accessibility. القبول: اختبار ترحيل زائر الى مسجل + اختبار تعارض + اختبار حذف بيانات الزائر.

**6 - Dynamic Visual System - نظام بصري ديناميكي (12 صندوق + KPI Strip)**
المشكلة: الواجهات تتفاوت بين الادوات. التصميم: ترتيب ثابت لكل اداة: KPI Strip اولا، ثم 12 صندوقا بالترتيب المعتمد في R3/R4 (Primary Result + Formula/How Calculated + Inputs Summary + What-If + Sensitivity + Warnings/Safety + Cross-Tool Links + Evidence/Sources + Export + History + Feedback/Rating + Next Actions). حالات Loading/Skeleton + Error/Retry + Empty + Success موحدة. Mobile-first + Keyboard + Screen Reader. القبول: اختبار يعد 12 صندوقا بالترتيب + اختبار A11y + لقطات Mobile/Desktop.

**7 - Dynamic Navigation & Deep Links - تنقل ديناميكي وروابط عميقة**
المشكلة: الفهرس والفئات والادوات غير مترابطة بعمق. التصميم: الفهرس: Single Click = scrollIntoView للفئة، Double Click = router.push الى صفحة الفئة. كل اداة لها Deep Link مستقر: /smarttools/[category]/[toolId]?state=... + Breadcrumb + Prev/Next داخل الفئة + بحث فوري بالاسم والفئة والوسم. صفحة الفئة تعرض 18 اداة + حالة كل اداة (Live/Planned/Blocked). القبول: اختبار تنقل + اختبار Deep Link + اختبار ان الـ 111 القديمة ما زالت تعمل.

### مجموعة ب: الذكاء الاصطناعي - AI (8-14)

**8 - AI Provider Abstraction + Model Registry - تجريد المزود وسجل النماذج**
المشكلة: قفل مورّد واحد + لا ادارة اصدارات. التصميم: طبقة Provider واحدة بواجهة موحدة (chat/complete/embed/rerank). Model Registry: modelId + provider + version + capabilities + costPer1k + latencyP95 + evalScore + status (Active/Deprecated/Blocked) + allowedTenants + allowedUseCases. تبديل المزود/النموذج من اعدادات دون تغيير كود الادوات. لا يصبح اي مزود نقطة فشل وحيدة. القبول: Registry يعرض كل نموذج + اختبار Fallback عند تعطل مزود + اختبار منع استخدام نموذج Blocked.

**9 - RAG بمصادر واضحة - Retrieval مع Citations و Freshness وعزل المستاجر**
المشكلة: اجابات بلا مصدر = هلوسة. التصميم: فهرس منفصل لكل مستاجر (Tenant-Isolated Index)، لا خلط بين مستاجرين. كل مصدر له: sourceId + title + urlOrRef + publisher + publishedDate + reviewedDate + evidenceLevel + allowedUse. الاجابة تحمل: Citations قابلة للنقر + تاريخ المصدر + درجة الثقة + ما هو غير معروف. سياسة Freshness: مصادر قديمة تظهر تحذير Stale. لا يرسل للـ RAG بيانات PII دون موافقة وتصنيف. القبول: اختبار يثبت ان كل اجابة RAG لها مصدر + اختبار عزل مستاجر + اختبار Stale.

**10 - AI Policy Engine قبل/بعد النموذج + دفاع ضد حقن التعليمات + اخفاء PII**
المشكلة: مدخلات غير موثوقة + حقن + تسرب PII. التصميم: Pre-Model: فحص المدخل (نوع/حجم/حقن/محتوى محظور/PII) + تصنيف حساسية + قرار (سماح/تنقية/حظر). Post-Model: فحص المخرج (هلوسة/مصدر/محتوى طبي غير امن/PII/نبرة) + اضافة تحذيرات + Citations. PII Redaction قبل الارسال للمزود. كل مدخل نص/صورة/ملف/رابط يعامل كبيانات غير موثوقة. القبول: اختبار حقن سلبي + اختبار PII + اختبار مخرج طبي غير امن يتم حظره او تحذيره.

**11 - AI Evals - مجموعات تقييم ذهبية وبوابات تراجع**
المشكلة: لا دليل على ان AI تحسن. التصميم: Golden Datasets لكل فئة: اسئلة + اجابة مرجعية + مصادر + حالات حدودية + حالات Red Flag. مقاييس: Grounding (هل الاجابة مدعومة بالمصدر؟) + Hallucination Rate + Safety Pass + Citation Precision + Latency + Cost. كل تغيير نموذج/موجه/مصدر يمر بـ Eval في CI، واي تراجع يمنع الدمج. القبول: Eval Suite يعمل في CI + تقرير Eval مع كل اصدار نموذج.

**12 - AI Cost / Quality / Latency Monitoring - مراقبة الجودة والتكلفة والزمن**
المشكلة: فاتورة مفاجئة + تدهور صامت. التصميم: لكل طلب: tokens + cost + latency + model + tenant + tool + evalScore + feedback. Budgets لكل مستاجر/اداة/شهر + Quotas (طلبات/دقيقة) + Cost Attribution. تنبيه عند 80% + ايقاف ناعم (Fallback حتمي، ليس قطعا مفاجئا) عند السقف الا بموافقة مالك. لوحة Quality: تتبع تدهور Grounding او زيادة الشكاوى. القبول: اختبار تجاوز ميزانية + تنبيه 80% + تقرير تكلفة شهري.

**13 - AI Memory - ذاكرة قابلة للحذف، بموافقة، وبنطاق ضيق**
المشكلة: ذاكرة بلا حدود = تسرب وخصوصية. التصميم: ذاكرة لكل مستخدم فقط، بموافقة صريحة قابلة للسحب، قابلة للعرض والحذف والتصدير. انواع: تفضيلات + حقائق ادخلها المستخدم + سياق اداة - ابدا اسرار او بيانات طبية حساسة دون تصنيف وموافقة. TTL + حذف تلقائي عند سحب الموافقة. لا ذاكرة مشتركة بين المستخدمين. القبول: اختبار حذف الذاكرة + اختبار سحب موافقة + اختبار عدم تسرب بين مستخدمين.

**14 - AI Multimodal Pipeline - معالجة الصور والملفات بامان**
المشكلة: ملفات وصور غير موثوقة. التصميم: تحقق نوع/حجم/امتداد + مسح حيث يتاح + عزل معالجة (Sandbox) + استخراج نص/قياسات فقط، بلا تنفيذ تلقائي. مثال: صورة تحليل مختبر = استخراج ارقام + مقارنة بنطاقات مرجعية عامة + تحذير انه تثقيف وليس تشخيص + احالة طبية. لا يحوّل صورة ناقصة الى وصفة. القبول: اختبار ملف ضار + اختبار صورة ناقصة + اختبار PII في صورة.

### مجموعة ج: عام للادوات والسحابة - General Tools & Cloud (15-20)

**15 - Cloud Tenant Isolation - عزل المستاجرين**
المشكلة: بلا عزل مثبت. التصميم: كل مستاجر له tenantId في كل جدول/فهرس/مفتاح تخزين/سجل. RLS في قاعدة البيانات + فحص tenant في طبقة التطبيق (Defense in Depth) + مفاتيح تشفير لكل مستاجر حيث يتاح + فصل مفاتيح التخزين (Prefix per Tenant). اختبارات Negative اجبارية: مستاجر A يحاول قراءة/كتابة بيانات B فيفشل. القبول: اختبار اختراق RLS + تقرير عزل.

**16 - IAM - الهوية والصلاحيات RBAC/ABAC + Secrets Vault + Audit**
المشكلة: صلاحيات غير موثقة. التصميم: ادوار: Owner + Admin + Developer + Reviewer + Support (Read-only) + User. RBAC للادوار + ABAC للشروط (tenant + tool + time + sensitivity). Secrets في Vault فقط، بلا اسرار في الكود او السجلات. كل فعل مؤثر يسجل: من + ماذا + متى + من اي جهاز + نتيجة. مراجعة صلاحيات دورية. القبول: اختبار صلاحية لكل دور + اختبار منع تصعيد صلاحية + سجل تدقيق قابل للتصدير.

**17 - Queues + Workers + Streaming + Idempotency - صفوف مهام**
المشكلة: مهام طويلة بلا ادارة. التصميم: Job Types: AI Explain + Export + Import + Eval + Indexing + Backup. كل Job له: jobId + idempotencyKey + retryPolicy (3 محاولات بتراجع اسي) + timeout + DLQ + status (Queued/Running/Done/Failed). بث نتائج (Streaming) للمهام الطويلة مع الغاء. لا ازدواجية: نفس Idempotency Key = نفس النتيجة. القبول: اختبار Retry + DLQ + Idempotency + الغاء.

**18 - Observability - قابلية المراقبة (Logs/Metrics/Traces + SLOs)**
المشكلة: اعطال صامتة. التصميم: Logs منظمة (JSON) بلا PII/اسرار + Metrics (Latency/Error/Cost/Queue Depth) + Traces (RequestId عبر كل طبقة). SLOs ملزمة: مثال P95 Latency + Error Rate + Availability لكل اداة حرجة. Dashboards: Health + AI Quality + Cost + Queues. تنبيهات: تجاوز SLO + DLQ + تدهور Eval. القبول: Dashboard حي + تنبيه مجرب + RequestId يتتبع عبر الطبقات.

**19 - Backup / Restore / DR - نسخ احتياطي واستعادة وكوارث**
المشكلة: نسخ بلا استعادة مجربة. التصميم: نسخ يومي مشفر + PITR (استعادة لنقطة زمنية) + نسخة خارج المنطقة + اختبار استعادة دوري (DR Drill) بـ RPO/RTO مقاسين. عمليات Data Subject: تصدير/حذف بيانات المستخدم عند الطلب مع سجل. لا نسخ احتياطي يحتوي اسرارا غير مشفرة. القبول: تقرير Drill استعادة فعلي + اختبار تصدير/حذف + RPO/RTO موثقان.

**20 - CI/CD + Feature Flags + Gradual Rollout + Kill Switches - اطلاق تدريجي امن**
المشكلة: اطلاق شامل بلا رجوع. التصميم: CI: Typecheck + Lint + Unit + Contract + Eval + A11y + Security Scan (SBOM/Deps) - اي فشل يمنع الدمج. CD: بيئات Dev - Staging - Prod معزولة + موافقات. Feature Flags: flag + owner + rollout% + conditions + expiry. Canary: 1% ثم 10% ثم 50% ثم 100% مع معايير تراجع تلقائي (Error/Latency/Cost). Kill Switches: لكل AI/اداة/مزود، تفعيل في اقل من دقيقة + Fallback حتمي. Rollback: Migration قابلة للتراجع حيثما امكن + خطة رجوع موثقة. القبول: اطلاق Canary مجرب + Kill Switch مجرب في Game Day + Rollback مجرب.


## 3. طبقة التطوير السحابي الاحترافية - Cloud Genius Professional Layer (تفصيل تشغيلي)
هذه الطبقة تحويل الاقتراحات العشرين الى عقود تشغيلية. كل بند له: الهدف، العقد، الممنوع، الدليل المطلوب.

### 3.1 عزل المستاجرين - Tenant Isolation
الهدف: مستاجر لا يرى ولا يعدل بيانات مستاجر اخر ابدا. العقد: tenantId في كل سجل/فهرس/مفتاح/سجل تدقيق. RLS في DB + فحص tenant في التطبيق + مفاتيح تخزين ببادئة Tenant. الممنوع: استعلام بلا tenantId، او فهرس مشترك بلا فلتر tenant، او Cache مشترك بلا مفتاح tenant. الدليل: اختبارات Negative + تقرير عزل + مراجعة RLS.

### 3.2 ادارة الهوية والصلاحيات - IAM (RBAC/ABAC)
الهدف: اقل صلاحية ممكنة لكل شخص وخدمة. العقد: ادوار + شروط ABAC (tenant + tool + sensitivity + time). كل خدمة لها هوية وصلاحيات محدودة، لا هوية خارقة مشتركة. Secrets في Vault مع تدوير. الممنوع: اسرار في الكود/السجلات/البيئة المكشوفة، او صلاحية Admin دائمة لشخص واحد. الدليل: مصفوفة صلاحيات + اختبار تصعيد سلبي + سجل تدقيق.

### 3.3 سجل نماذج AI - AI Model Registry
الهدف: كل نموذج معروف الاصدار والتكلفة والتقييم والحالة. العقد: سجل مركزي يحمل modelId/version/provider/capabilities/cost/latency/eval/status/allowedUse. لا استدعاء نموذج غير مسجل. التراجع لاصدار سابق ممكن في دقائق. الممنوع: نموذج بلا Eval، او تبديل نموذج في الانتاج بلا موافقة و Eval. الدليل: صفحة Registry + سجل تغييرات + تقرير Eval لكل اصدار.

### 3.4 RAG بمصادر واضحة
الهدف: كل اجابة ذكاء قابلة للتحقق من مصدرها. العقد: مصادر معتمدة فقط + Citations + تاريخ + ثقة + Freshness + عزل فهرس لكل مستاجر. لا اجابة طبية بلا مصدر وتحذير. الممنوع: مصدر مجهول، او مصدر منتهي بلا تحذير Stale، او خلط فهارس المستاجرين. الدليل: مثال اجابة مع Citations + اختبار عزل + اختبار Stale.

### 3.5 مراقبة الجودة والتكلفة - Quality & Cost Monitoring
الهدف: لا فاتورة مفاجئة ولا تدهور صامت. العقد: مقاييس لكل طلب (tokens/cost/latency/grounding/feedback) + Budgets/Quotas + Cost Attribution لكل مستاجر/اداة. تنبيه 80% + ايقاف ناعم عند السقف. لوحة جودة تتتبع Hallucination و Grounding ورضا المستخدم. الممنوع: اطلاق AI بلا Budget، او تجاهل تدهور الجودة اسبوعا كاملا. الدليل: لوحة + تنبيه مجرب + تقرير تكلفة شهري.

### 3.6 تقييمات - Evals
الهدف: اثبات ان AI تحسن او على الاقل لم يتراجع. العقد: Golden Sets + مقاييس Grounding/Hallucination/Safety/Citation + بوابة CI تمنع التراجع. كل نموذج/موجه/مصدر جديد يمر بـ Eval قبل الانتاج. الممنوع: تغيير موجه في الانتاج بلا Eval. الدليل: تقرير Eval + سجل CI.

### 3.7 مفاتيح ايقاف - Kill Switches
الهدف: ايقاف اي AI/اداة/مزود في اقل من دقيقة. العقد: مصفوفة Kill Switch: الاسم + النطاق + المالك + زمن التفعيل + Fallback + اجراء الاعلام. Fallback حتمي: محرك حسابي + رسالة واضحة، ليس ادعاء AI بديل. تجربة Game Day دورية. الممنوع: AI بلا Kill Switch، او Fallback يدعي انه AI. الدليل: سجل Game Day + زمن ايقاف مقاس.

### 3.8 صفوف مهام - Task Queues
الهدف: مهام موثوقة لا تضيع ولا تتكرر. العقد: Job + IdempotencyKey + Retry + Timeout + DLQ + Status + Streaming + Cancel. الممنوع: مهمة بلا Idempotency، او اعادة محاولة بلا سقف، او DLQ بلا مراقبة. الدليل: اختبار Retry/DLQ/Idempotency.

### 3.9 Observability - قابلية المراقبة
الهدف: رؤية كل طلب من الواجهة حتى المزود. العقد: RequestId واحد عبر الطبقات + Logs منظمة بلا PII + Metrics + Traces + SLOs + Alerts + Dashboards. الممنوع: سجلات تحوي PII/اسرار، او SLO بلا تنبيه. الدليل: Dashboard + تنبيه مجرب + تتبع RequestId.

### 3.10 نسخ احتياطي - Backup & DR
الهدف: استعادة مثبتة وليست نظرية. العقد: نسخ يومي مشفر + PITR + نسخة خارج المنطقة + Drill دوري بـ RPO/RTO مقاسين + عمليات تصدير/حذف للمستخدم. الممنوع: نسخ بلا Drill، او نسخ تحوي اسرارا غير مشفرة. الدليل: تقرير Drill + اختبار تصدير/حذف.

### 3.11 CI/CD
الهدف: لا كود مكسور يصل للانتاج. العقد: CI يفحص Typecheck + Lint + Unit + Contract + Eval + A11y + Security (SBOM/Deps). CD ببيئات معزولة + موافقات + Migrations قابلة للتراجع. الممنوع: دمج بلا CI اخضر، او نشر انتاج بلا موافقة مالك محددة النطاق. الدليل: سجل CI + سجل نشر + خطة رجوع.

### 3.12 Feature Flags والاطلاق التدريجي - Flags + Gradual Rollout
الهدف: اطلاق امن قابل للتراجع. العقد: كل ميزة جديدة خلف Flag (مالك + نسبة + شروط + انتهاء). Canary 1% ثم 10% ثم 50% ثم 100% مع معايير تراجع تلقائي (Error/Latency/Cost/Feedback). مراجعة Flags دورية لحذف المنتهية. الممنوع: اطلاق 100% من اول يوم لميزة AI جديدة، او Flag بلا مالك او انتهاء. الدليل: سجل اطلاق Canary + سجل Flags.

### 3.13 طبقة AI واسعة السياق بلا سقف وظيفي اعتباطي - Wide-Context AI (مع ضوابط)
المبدأ: لا يفرض سقف اصطناعي ثابت على طول السياق او عدد الوثائق او عمق التحليل متى كانت البنية والميزانية والتفويض تسمح بذلك. القدرة على التحليل لا تمنح حق الوصول الى بيانات المستخدمين او الاسرار او الانتاج او اتخاذ افعال مؤثرة دون تفويض وموافقة. التصميم: سياق متدرج (Summarization + Retrieval + Chunking + Citations) + Budgets للسياق والتكلفة + Policy Engine + Audit. كل توسيع للسياق يجب ان يحترم: الهوية، اقل صلاحية، موافقة المستخدم، الخصوصية، القانون. الممنوع: استخدام سعة السياق كمبرر لتجاوز الصلاحيات او ارسال بيانات حساسة لمزود بلا موافقة. الدليل: اختبار سياق واسع + اختبار صلاحية + سجل تدقيق.

### 3.14 الصحة والسلامة - Safety (تثقيف لا وصفة)
المبدأ: النظام يقدم تثقيفا عاما، تفسيرا للمخاطر، اسئلة توضيحية، وتنبيها للرعاية الطبية عند الحاجة. لا يحول معلومات ناقصة الى وصفة شخصية، ولا يخفي عدم اليقين او موانع الاستخدام. Red Flags: كل حالة حرجة تظهر تحذيرا واضحا + احالة طبية + منع اكمال اجراء خطر. لا توصيات جرعات او دورات او بروتوكولات شخصية. كل محتوى صحي يحمل: مصدر + تاريخ + حدود + تحذير. القبول: اختبار Red Flag + مراجعة محتوى صحي + سجل تحذيرات.
